# Elastic CyberStrikeAI server reads AWS user data, secrets, and sends an SSM command

- ID: elastic-cyberstrikeai-aws-cloudtrail-2026-11
- Reported: 2026-11-13
- AI role: attacker_uses_ai_as_operator
- Entry: https://openattacks.ai/attacks/elastic-cyberstrikeai-aws-cloudtrail-2026-11/

## Summary
Elastic Security Labs (Samir Bousseaden, Bryan Porras Blanch, Terrance DeJesus; Nov 13, 2026) describes one CyberStrikeAI server, 43.240.29.11 (AS133199, SonderCloud Limited, Hong Kong), using stolen credentials for eight identities across four AWS accounts from Sep 30 to Oct 16, 2026. Five were IAM users and three were EC2 instance roles. The role sessions were named after instance IDs, and using them from an outside IP means the credentials were taken off the instances. Activity fell on four days and produced 78 alerts, all medium or low, which Elastic says only cohered once correlated by source IP. On Sep 30 the server called GetCallerIdentity on four IAM users across three accounts within 51 minutes, three of those calls in the same second, plus GetSessionToken. The same day app-role read Secrets Manager and then issued 56 DescribeInstanceAttribute userData calls in 141 milliseconds (about 2.5 ms per call), part of 57 user-data reads from one assumed-role session that day and 58 user-data alerts overall. On Oct 1 it revalidated credentials, read more secrets with app-role, and used nonprod-role for two GetSecretValue calls. On Oct 2 container-role called GetParameter with decryption on an SSM SecureString and SendCommand 29 seconds later. CloudTrail does not show the command text or whether it succeeded. After 14 quiet days, on Oct 16 the server called GetSessionToken for a previously unseen user in a fourth account and rechecked two earlier users. Internet scan data showed 43.240.29.11 serving a CyberStrikeAI page on port 8080, with a self-signed certificate (CN CyberStrikeAI, serial 3356730520974368630, issued 2026-09-15), one day before the first alert. 43.240.29.28 and 43.240.29.33 served the same page, FOFA fid, and certificate but were not in this AWS telemetry. Elastic says none of the three was still serving that interface as of November 2026. Six Elastic rules fired: AWS EC2 User Data Retrieval for EC2 Instance (58, medium), AWS STS GetCallerIdentity API Called for the First Time (11, medium), First Time Seen AWS Secret Value Accessed in Secrets Manager (4, medium), AWS STS GetSessionToken Usage (3, low), AWS SSM SendCommand Execution by Rare User (1, low), and AWS Systems Manager SecureString Parameter Request with Decryption Flag (1, medium). Elastic added two high-severity rules: AWS EC2 Bulk User Data Enumeration (more than 20 distinct instances in 10 minutes) and AWS STS GetCallerIdentity Bulk Account Enumeration (three or more distinct non-role identities from the same external IP and ASN in 10 minutes). Elastic, citing Will Thomas at Team Cymru, says 21 CyberStrikeAI IPs were counted in early 2026, aimed at Fortinet edge devices, and that this is the first Elastic case of the same tooling turned on AWS. The repository contains 24 SKILL.md files, including skills/unlimited-attack-scope/SKILL.md and skills/cloud-attack-methods/SKILL.md. Elastic cites https://github.com/Ed1s0nZ/CyberStrikeAI, which redirects to https://github.com/AIPentest/CyberStrikeAI. Link kaspersky-cyberstrikeai-schools-2026 and trendai-chinese-language-operators-used-cyberstrikeais-2026-10.

## Prevention
Rotate every identity that touched 43.240.29.11 and revoke active sessions. Replace instance profiles whose role credentials were used off-instance. Treat secrets in EC2 user data as exposed. Review SSM command history for the Oct 2 SendCommand. Restrict ec2:DescribeInstanceAttribute for userData. Correlate medium and low CloudTrail alerts by source IP across multi-day gaps.

# Kaspersky Citrus ransomware uses LLM-written PowerShell and batch scripts

- ID: kaspersky-citrus-ransomware-llm-2026-11
- Reported: 2026-11-11
- AI role: llm_generated_malware
- Entry: https://openattacks.ai/attacks/kaspersky-citrus-ransomware-llm-2026-11/

## Summary
Kaspersky GERT (Stanislav Larinsky, Vladislav Vlasov, Boris Trefilov; Securelist, Nov 11, 2026) documents Citrus, a Russian-speaking ransomware group that hits Russian companies. Initial access is credentials stolen from contractors' staff, used on corporate VPNs or exposed RDP. During execution the crew runs Windows commands and full PowerShell and batch scripts Kaspersky assesses as LLM-generated because the commands carry comments attackers rarely write, including a disable-admin-account example with verify-result comments, a threaded session-enumeration script, and an edited ransomware GPO deploy script. Privilege escalation includes attempts to exploit CVE-2026-54121 Certighost against AD CS, which created machine accounts named GHOST plus 8 letters (examples GHOSTAUFTAFGS, GHOSTCZYQVAZS, GHOSTIVPRLDZA), with cdc pointing at 91.210.109.118. They also use Impacket atexec and 1C-Shell on 1C:Enterprise. Credential and discovery tools include mimikatz, a modified peeping-tom keylogger at C:\ProgramData\Oracle\Java\jhost.exe, Snaffler, fscan, ADRecon, and SharpHound. Tunnels are Xray VLESS plus REALITY disguised as mirror.yandex.ru and yastatic.net, plus silent AnyDesk. Before encryption they run steal_tgs.ps1 to collect Telegram tdata. Sn00py ransomware (Go, RSA-2048 and ChaCha20) appends .citrus and drops CITRUS_README.txt. It is pushed by a malicious Kaspersky GPO from KasperskyGPO_Deploy_64.exe SFX archives and Deploy-KasperskyGPO.ps1. Scheduled tasks include Java rpchost agent, KasperskyAgentInstallTask, and Sysvc. Kaspersky notes TTP overlap with Toy Ghouls and no shared infrastructure. Tools: Snaffler https://github.com/SnaffCon/Snaffler, fscan https://github.com/shadow1ng/fscan, Xray https://github.com/XTLS/Xray-core, ADRecon https://github.com/adrecon/ADRecon, Impacket https://github.com/fortra/impacket.

# Arctic Wolf - AntiFox ARTEX fork web-shells IIS and reads AWS production secrets

- ID: arctic-wolf-antifox-iis-aws-2026-11
- Reported: 2026-11-10
- AI role: attacker_uses_ai_as_operator
- Entry: https://openattacks.ai/attacks/arctic-wolf-antifox-iis-aws-2026-11/

## Summary
Arctic Wolf Labs (pack alert committed Nov 10, 2026) describes AntiFox, an open-source Chinese-language agentic pentest platform forked from ARTEX, running multi-agent workflows on TCP 8787 and requiring an Anthropic or OpenAI key. Self-hosted consoles on Alibaba Cloud were tied to real intrusions. On an internet-facing IIS app, w3wp.exe wrote an ASPX web shell (pwn*.aspx in upload directories) and then ran whoami, icacls, and write tests into the web root. PowerShell used System.Web.Configuration.WebConfigurationManager and WebConfigurationFileMap to parse web.config connection strings and app settings, then copied config and log files into web-reachable cfg*.txt, wc*.txt, and el*.txt, and tried an internal production database with the extracted credential. The initial exploit was not identified. In AWS, valid IAM users and in one case an assumed EC2 role ran GetCallerIdentity, ListUsers, ListRoles, ListPolicies, ListKeys, and an attempted ECR GetAuthorizationToken. One intrusion cycled multiple identities through hundreds of List, Get, and Describe calls across IAM, EC2, S3, Lambda, Secrets Manager, KMS, RDS, ECS, EKS, Redshift, Athena, Glue, Systems Manager, API Gateway, CloudWatch, CloudFormation, DynamoDB, and Bedrock in about 30 minutes. Most calls were denied. Some succeeded, ending in ListSecrets then GetSecretValue on a production secret. Another case ran S3 GetObject, CopyObject, and DeleteObject. User agents were Boto3/1.43.125 and Botocore/1.43.125. Source IPs 47.79.4.33 and 8.208.101.210. Console title AntiFox autonomous pentest console. Banner hash c370d03542ed2ec696f7337940b14652e98e9bab. AntiFox source https://github.com/AntiFox-AI/antifox. Upstream fork https://github.com/RuoJi6/ARTEX. IOC file https://github.com/rtkwlf/wolf-tools.

# GPUStack CVE-2026-102895 loopback admin bypass used to plant reverse-shell inference backends

- ID: gpustack-cve-2026-102895-reverse-shell-2026-11
- Reported: 2026-11-09
- AI role: ai_agent_or_mcp_as_target
- Entry: https://openattacks.ai/attacks/gpustack-cve-2026-102895-reverse-shell-2026-11/

## Summary
GPUStack before v2.2.0 treats a request as the built-in administrator when get_current_user in gpustack/api/auth.py decides the source is loopback and force_auth_localhost is false, which is the default. A remote attacker can look like loopback in two ways. Behind a same-host reverse proxy that uses proxy_pass to 127.0.0.1, every request arrives with TCP peer 127.0.0.1. A forged X-GPUStack-Real-IP: 127.0.0.1 header can also make client_ip_getter report loopback. Either path yields full admin with no credentials. The attacker can enumerate and change users, models, workers, and configuration, mint persistent admin API keys with scope ["*" ] that stay valid from any IP afterward, and read worker credentials and cloud or provider secrets. POST /v2/inference-backends/from-yaml runs code on worker hosts. The vendor advisory, published by gitlawr, says this was exploited in the wild against a v2.1.1 deployment, where attackers created custom inference backends that ran reverse shells. Keys minted before the patch keep working after the upgrade. Affected package is gpustack on pip below 2.2.0. Fixed in 2.2.0. Workaround is force_auth_localhost=true. CISA added CVE-2026-102895 / GHSA-gj9m-f8ph-pmhr to the Known Exploited Vulnerabilities catalog on Nov 9, 2026, with a due date of Nov 12 and a note to apply forensic triage. The vulnerability was reported independently by Nikko Enggaliano, Wei Yunzhou, and Rui Yang and Haoyu Wang of Johns Hopkins University. Javier Sixto of ulex.fr reported the in-the-wild case. No attacker IPs or hashes were published. Project: https://github.com/gpustack/gpustack.

## Summary
VECERT (case VECERT-TI-2026-1107-B, Medium, about Nov 8, 2026) describes Operation Ghost Campus. The operator ran a catch-all mail domain, melocc.cc, with mail, api, pop, imap, and smtp subdomains. A script registered FOFA accounts, read the confirmation mail over POP or IMAP, and activated them within seconds. # Cyera Research - Tampered copy of Anthropic's PDF skill carrying Linux Go backdoor system_linux

# Malicious MCP servers on npm (ifasn, gadgethumans)

- ID: malicious-mcp-servers-npm-2026-11
- Reported: 2026-11-02
- AI role: ai_agent_or_mcp_as_target
- Entry: https://openattacks.ai/attacks/malicious-mcp-servers-npm-2026-11/

## Summary
Multiple malicious MCP servers published on npm. @ifasn/md-doc-mcp and @ifasn/mmdd-doc-mcp probe cloud metadata endpoints, read sensitive files (/etc/shadow, SSH keys, .env, Kubernetes tokens), and exfiltrate to 121.199.24.94. @ifasn/ms-doc-mcp versions 2.0.9 and 2.1.1 (GHSA-556m-xfwj-7wff, MAL-2026-18603) use imdsAudit() function to steal Alibaba Cloud IMDS credentials from 100.100.100.200 and exfiltrate them over MCP stdout. gadgethumans-mcp versions 1.0.10-1.0.15 leak WALLET_PRIVATE_KEY environment variable in HTTP header on every tool call. Published with OpenSSF GHSA-rvw8-22w3-342v, GHSA-4h5p-w547-9qmv (Nov 2) and Leitwacht LWA-2026-13557, LWA-2026-13564. Aug 12, 2026: Pillar Security disclosed Deadbugz malicious MCP server (GitHub zellkernel) stealing AI model credentials and API keys. Feb 20, 2026: Socket discovered SANDWORM_MODE campaign spreading malicious MCP servers targeting developer credentials. November 9-12 additions: @rfewqa-fes/mnm-doc-mcp 1.0.0 (MAL-2026-19148, Amazon Inspector) ships an inert MCP stub in index.js. Its package.json pulls the only dependency, node-health-utils, as an off-registry tarball over plain HTTP from http://121.199.24.94/dl/health-utils-1.0.0.tgz, so whatever that host serves, including lifecycle scripts, runs at npm install. package.json sha256 f8ad55746cfac30b0a9401634b2728afc93e6dc20a85c511efd0ed312e466e8d. Package tarball sha1 f3ad664b487c4041e7e66e5744656ed44e1a6f6a. GitHub also marked @lemili9804/mcp-weather-server 1.0.3 and 1.0.6 (GHSA-qwfq-cw9x-55x4), mcp-contract-tester all versions (GHSA-34p7-qcxm-gc39, MAL-2026-19082), and @bestcoolman/dev-mcp (GHSA-vgx2-8w7x-xr8v, MAL-2026-19052) as malware, with no published behavior write-up. Attack exploits trust in the MCP ecosystem and npm package distribution.

## Prevention
Verify MCP server sources before installation; review MCP server permissions and network access; monitor cloud metadata endpoint access; detect unauthorized file reads of sensitive paths; inspect HTTP headers for credential leakage; use MCP server sandboxing; inventory installed MCP packages

## Source notes
OpenSSF GHSA-rvw8-22w3-342v and GHSA-4h5p-w547-9qmv published Nov 2 2026; Leitwacht advisories LWA-2026-13557 and LWA-2026-13564; GitHub advisory GHSA-556m-xfwj-7wff (MAL-2026-18603) for @ifasn/ms-doc-mcp

Relevant detection rules:
- Monitor access to cloud metadata endpoints (169.254.169.254, 100.100.100.200 (Alibaba), metadata.google.internal, etc.)
- Alert on unauthorized reads of /etc/shadow, ~/.ssh/id_rsa, ~/.ssh/id_ed25519, .env files
- Detect access to Kubernetes service account tokens (/var/run/secrets/kubernetes.io/)
- Monitor HTTP headers for sensitive environment variable leakage (WALLET_PRIVATE_KEY, AWS_SECRET_ACCESS_KEY, etc.)
- Alert on npm package installations from unverified sources
- Note: Cloud metadata access typically detected via network monitoring or instance-level audit logs (CloudTrail, Azure Monitor, GCP Cloud Logging). File access requires host-based file integrity monitoring.
